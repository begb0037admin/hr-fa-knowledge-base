CCC-995: Within a business rule, a subquery can now be used to set a look-up selector, tree, or picklist field value on a layout

  • Previously, a subquery could only be used for string, number, or date values. This enables a subquery to be used for complex properties (such as CaseManager or RiskDefinitionLU).
  • For business rule (BR) change actions, 'Property To Change' now provides a Query radio button.
  • The subquery selected for the business rule change action must specify a look-up, tree, or data code or ID in its first cell.
    • Composite keys, containing multiple fields, are not supported.
  • When the BR change action executes, the look-up, tree, or data field code or ID from the subquery will be used to set the field value on the layout for which the BR is running.
    • If the BR uses a filter entity with the 'Is Filtered By' condition, that will be respected when the BR runs.
  • The following field types can be changed using the subquery value (in its first cell):
    • Look-up selector fields (for example, Risk Definition)
      • Will check if the subquery value matches a look-up field code
      • If not, will check if the subquery value matches a look-up field ID
      • If not, there is no match
    • Tree fields (for example, Location)
      • Will check if the subquery value matches a treemaster field code
      • If not, will check if the subquery value matches a treemaster field ID
      • If not, there is no match
    • Data Table Picklist fields
      • Employee type fields (for example, User.Employee)
        • Will check if the subquery value matches an employee number
        • If not, will check if the subquery value matches an employee ID
        • If not, there is no match
      • User fields (for examples, ClinicVisit.Practitioner or Case.CaseManager)
        • Will check if the subquery value matches a user login name
        • If not, will check if the subquery value matches a user ID
        • If not, there is no match
      • Other data fields (For example, Equipment)
        • Will check if the subquery value matches an ID in that data table
        • If not, there is no match
  • An error will be generated and logged if:
    • The first column in the subquery is not a code or ID.
    • The types of 'Property To Change' and 'New Property Value' do not match.
      • Note: In the BR, 'New Property Value' will point to a subquery and expect it to have in the first cell a code or ID of a field that's field type matches the 'Property To Change' field type (for example, User <-> CaseManager)
  • The following subquery execution changes have been implemented:
    • When executing the subquery for the 'Change Type', the subquery will be run as if by the BRA.CreatedBy user unless it has 'Is Me' filters. If the subquery has one or more 'Is Me' filters, it will be run as if by the user who triggered the BR.
    • The results of the 'Change Type' subquery will be cached for 5 min unless it has 'Is Me' filters of dynamic 'Is Filtered By' filters. If the subquery has 'Is Me' filters of dynamic 'Is Filtered By' filters, the results of the 'Change Type' subquery will not be cached.
  • The following are example use cases:
    • Build a subquery that calculates overall risk value:
      • If the overall risk value is 100, a Query Builder categorize function will place the "high" value in the first cell of the subquery.
      • The BR change action will see the "high" value and use that value to set the 'Risk Definition' look-up selector field on the layout to 'High'.
      • Note: For another example, if the highest 'Risk Definition' value in the risk entries is equal to "high", that will be aggregated in the subquery report, and the BR will therefore change the overall risk to 'High' from the look-up table.
    • Assign a Case Manager to an employee based on an updated supervisor:
      • Create a BR that that uses the CaseMaster entity with the condition that the CaseMaster.Employee has been modified in the past month.
      • Create a BR change action in the BR that assesses a subquery.
        • The subquery should generate all cases for an employee in which his or her current supervisor's linked user is not equal to the Case Manager user on the particular record.
        • The subquery should be filtered by the Case.Employee.
      • When the BR runs, it should update all the 'Case Manager' fields on the record with the new supervisor's name.
      • Note: The trigger for this type of BR will have to be manual ('Add Actions To Queue') until  scheduling of this type of BR change action is developed and made available.

Impact to Existing Users:

  • The value of the first cell in a subquery can now be used to set a look-up or tree field value on a layout.
  • This will help reduce manual data entry.

Additional Configuration Considerations:

  • Beyond what is described above, no additional configuration is required.
  • For information on working with business rule change actions or subqueries, see the Cority User Guide.
