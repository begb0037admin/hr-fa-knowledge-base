CCC-1040 and 3032: GET, POST, and PUT RESTful API calls now support document files

  • For business rule (BR) API actions, a new calculated merge field is now available at the document level.
    • The field can contain document data in the base64 string format.
    • The document data can be requested from or sent through the existing 'Document' RESTful API endpoint.
    • The user can GET/POST/PUT 'Document' metadata fields. That functionality was already available.
    • The user can now GET/POST/PUT 'Document' BLOB fields.
      • Each BLOB field will be returned as a base64 string.
      • The BLOB fields will not be returned by default. They must be called explicitly by using the Fields and/or AdditionalFields parameter (for example: ?Fields=documentId,DocumentBlob.DocumentData or ?AdditionalFields=DocumentBlobData, within the URL).
    • In a read GET, if DocumentBLOB is requested in the Fields parameter, then only one document record (the top result) will be returned at a time.
    • In an insert POST or update PUT, when a user provides a DocumentBlob for upload, the system will check/ensure that:
      • The 'Reference Type' field is set automatically based on the linked record.
      • Values for the following are provided:
        • DocumentBlobData
        • DocumentName (filename with an extension Cority accepts)
        • DocumentPreview (thumbnail that can be viewed within Cority)
      • Only one document per request is configured to be uploaded.
      • The file size is less than or equal to the value of the 'Document Size' system setting.
      • The 'DocumentBlobData' value is not an empty base64 string.
        • If it is, an error will occur with the following message: DocumentBlobData cannot be null or a transparent image.
      • All other logic for 'Document' fields and a 'Document' URL are respected. For example, only a 'Doc Link File' or 'Doc Import File' can be specified.
      • Document data 'Record History' will continue to work as expected.
      • You can link to another record:
        • With an ID (for example, CaseMaster : \{ Id = 123 }
        • With a unique key (for example, CaseMaster : \{ CaseNo = 123 }
        • Note: This is the minimum required to link a new document to an existing Clinic Visit, for example.
  • Also, employee photo imports are functional:
    • You can provide a POST/PUT request to the Employee endpoint that has a byte array in the Photo field in order to update an employee's photo.
    • You can provide a GET request to the Employee endpoint to have the employee's photo returned in a byte array.
  • In addition, an HL7 file (for Clinical/Drug Testing records, for example) or a document can now be imported as a file through the RESTful API with the multipart/form-data content type, instead of being imported through the RESTful API with the application/JSON content type, as a base64 string/byte array (raw data).
    • The proper file types and file content types will be accepted as they are in the front-end.

Impact to Existing Users:

  • A user can now use the RESTful API to request or insert/update documents in the Cority system.
  • The ability to import a file with the multipart/form-data content type instead of a base64 string/byte array will simplify the importing of HL7 files and of documents.

Additional Configuration Considerations:

  • Beyond what is described above, no additional configuration is required.
  • For information on working with documents, see the Cority User Guide. For information on working with HL7 files, see the Cority System Guide. For information on working with the RESTful API, see the Cority RESTful API Guide.
