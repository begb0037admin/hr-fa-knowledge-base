CCC-15370: For RESTful API integrations, OAuth 2.0 support has been enhanced

Opt-In

There is a new ‘Enable OAuth 2.0 Refresh Tokens’ global system setting. By default, it is not selected. When the setting is selected and an OAuth 2.0 access token is requested, a refresh token will be returned in addition to the access token.

For tracking OAuth 2.0 refresh tokens, the Administrator ‘Users’ module has a new ‘OAuth 2.0 Refresh Tokens’ tab. This tab is not available for reporting, cannot be imported into, and does not provide the Create/Clone View functionality.
To view OAuth 2.0 refresh tokens for other users, the user’s role must be granted the security.viewalloauth2token security action.

Also, there is a new ‘API Refresh Token Grace Period’ global system setting. By default, it is set to 0. It can be set from 0 up to 60 minutes. If the ‘Auto Refresh API Refresh Token’ system setting is selected and the RESTful API and refresh token A are used to request access token A, the access token is returned with refresh token B. Refresh token A becomes invalidated at that point, unless the grace period is greater than zero. If greater than zero, the refresh token will remain valid for the grace period. This is to account for server issues that would cause problems obtaining the access token (for example, the call fails so refresh token A becomes invalid but the user did not obtain refresh token B because of the failed call).
A maximum of two refresh tokens can be active at any time for a single refresh token ID. For example, if you have valid refresh token A, and you use it to obtain token B, token A expires in X minutes (depending on the number of minutes specified). If either token A or token B is then used to obtain a token C, token A will no longer be valid and token B will then be in the grace period.
Note: Even though you can have two refresh tokens for any refresh token ID, you can have multiple refresh token IDs. For example, a single user could have five refresh tokens corresponding to five refresh token IDs, but each individual refresh token can only have two active at any point.

As well, the expiration time for both access and refresh tokens can now be configured in system settings to be longer term. For example, if the refresh token is configured to be one year, the user will not have to log in manually each time he or she wants an access token. If a refresh token is requested, the user would therefore only have to log in using OAuth 2.0 once per year.

Note: For this functionality, the ‘Enable Refresh Token Logic for OAuth Token’ system setting must be selected. Otherwise, only an access token will be returned.
When the access token expires, the user can use the refresh token, Client ID, and Client Secret to obtain a new access token. If the ‘Auto Refresh API Token’ system setting is selected, a new refresh token will also be returned. If configured, the ‘API Refresh Token Grace Period’ system setting (as described above) will apply to this workflow.
When the refresh token expires, this process must be repeated.
