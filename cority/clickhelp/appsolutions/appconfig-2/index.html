App Configuration

Advanced Workflows (WAB) solutions require certain basic components for its functioning. The design of the App is flexible, and must only follow certain basic rules:

  1. There must be one Primary definition workflow.
  2. There may be a Secondary workflow that is a child of the Primary workflow type. Up to three levels (Parent, Child, Grandchild) are allowed.
  3. The App Config file defines the Primary and Secondary workflows, their names and the names of the associated action buttons in the App. The secondary workflow requirement can be disabled in the config file, which will result in that tab not being displayed in the user interface.

To build an Advanced Workflows (WAB) solution, these components will be needed:

  • Definition Workflows: One Primary definition workflow and one Secondary (child) definition workflow (unless disabled). There may be several child and grandchild workflow types, as needed. See Definition Workflows.
  • Roles must be defined for each of the workflow steps.
  • Workflow Policies may also be defined to initiate notifications. Each Policy will require an associated Notification Template.
  • Form Templates and Custom Fields: Form templates with custom fields are required to define the forms for each step in the workflows. Use the Form Designer to design the form display and functions to suit your process. Conditions may defined within the forms to show or hide fields and action buttons based on field values. See Form Designer.
  • User Permissions: User groups can be set up and associated with the Workflow Roles as needed. View/edit permissions to a form may be granted at the field level or to the form overall. User ability to perform certain actions in the App may also be controlled through workflow role permissions.
  • System Model Associations: (Optional) App Items may be associated with specific system model objects (Divisions, Facilities, Units or POIs). Workflow Overrides can then be applied to determine the users who belong to the roles and the notification policies that apply on the location basis. System Model associations are not required; the App will function without them. See System Model Associations.
