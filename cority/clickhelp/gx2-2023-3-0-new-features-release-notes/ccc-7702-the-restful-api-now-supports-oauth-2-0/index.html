CCC-7702: The RESTful API can now use OAuth 2.0 authorization

  • The following authentication methods are supported:
    • LDAP/LDAPS
    • UserPass/2FA
    • SAML 2.0
    • Mixed Mode
  • There is a new ‘Client Application’ (LU_GLB_OAuthApplication) look-up table. The table has a default layout with the following columns:
    • Client ID – This is auto-generated by the system and not editable.
    • Client Name – This is required, must be provided by the administrator, and supports a maximum of 200 characters. It is the unique key for the look-up table entry.
    • Client Secret – This is auto-generated by the system and not editable.
    • Redirect URL – This is required, must be provided by the administrator, and supports a maximum of 500 characters.
  • The OAuth 2.0 RESTful API functionality requires that your GX2 Administrator create a record in this table to register your organization’s API portal application (for example, Intel API Portal).
  • The new look-up table is categorized under the Demographics module and accessible to any user with a role that is granted either the SecurityModules.LookupTablesForAdmin or SecurityModules.LookupTables security action.
  • Note: A user’s role must be granted the new security.viewclientsecret security action for the user to view any client secrets he or she creates. A user’s role must be granted the new security.viewallclientsecret security action for the user to view all client secrets.
  • A new ‘OAuth 2.0 Access Tokens’ sublist can now be added to custom versions of the User layout. The sublist has a default ‘OAuth2.0 Access Token for this User’ view with the following columns: Client Name, Expiration, Access Token, Creation Date
  • Access Token values are prohibited from view unless a user is looking at his or her own User record or the user’s role is granted the security.viewalloauth2token security action.
  • The new sublist has the Delete and ‘Show Record History’ actions.
  • The sublist cannot be populated or updated using import.
  • Authorization request procedure:
  1. The client’s API portal application calls the new GX2 ‘OAuth 2.0 Login’ page.
  2. The application enters the Client ID that matches the one in the applicable ‘Client Application’ look-up table entry, a Callback URL the system will push the response to after successful authorization, and the State. The three are provided as parameters in the query to the OAuth login URL.
    The client application will (can only) choose Support Code as the response type.
  3. If not already logged in, the user will be directed to the login page or his or her SAML login process before continuing.
  4. After successful login, the following message will be presented to the user: Do you give <<Client Name>> access to READ, WRITE, UPDATE, and DELETE data from Cority? Yes/No
    The Client Name will be linked to the Client ID provided in step 2.
  5. If the user selects ‘Yes’, the system will push the request token and State parameter to the callback URL provided in Step 2.
    The authorization request token will be linked to the Client ID and have an expiration time of two minutes. It will be stored in the new ‘OAuth 2.0 Access Tokens’ sublist in the User table.
  6. If the user selects ‘No’, the system will redirect the user to the callback URL and display an error message.
    If your Client ID or Callback URL is invalid, an error message will display.
  • For access token requests, there is a new RESTful API endpoint (https://gx2api/oauth/token PostRequest). The endpoint requires:
    • Code – the authorization request token acquired in the procedure above
    • Client ID – the Client ID matching the one in the authorization request token
    • Client Secret – the Client Secret matching the one in the authorization request token
    • Grant Type – authorization_code
  • When the endpoint is called, it must match the authorization request token in the ‘OAuth 2.0 Access Tokens’ sublist of the user. If it does, the endpoint will return an access token. If it does not, the endpoint will return an invalid token message.
  • The acquired OAuth 2.0 access token can be used to access the RESTful API endpoints.
  • For specifying an inactivity time limit on OAuth 2.0 access tokens, there is a new ‘OAuth 2.0 Access Token Expiration’ system setting. The default value is 20 minutes.
  • If a user is inactive for the number of minutes specified in the setting, all of the user’s access tokens will expire.
  • If a user’s password is changed, all of the user’s access tokens will expire.
  • There is a maximum of ten access tokens per user at one time. If the maximum for a user is reached and a new token is added, the first token that was created will be deleted.
  • There is also a new, global ‘RESTful API Access Token Generation Method’ system setting.
  • The setting has the Refresh Token (default) and OAuth 2.0 options.
  • If set to Option 2 (OAuth 2.0), any refresh tokens that do not have a client ID and secret will not work. Note: OAuth 2.0 does not affect myCority.
  • If the method option in the setting is changed, access tokens generated by the other method will no longer be valid.
