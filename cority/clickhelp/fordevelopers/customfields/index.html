Custom Fields

Note: Custom fields are only available for the Management System EQL.

Custom Fields applied to an object are supported like native fields. For example, to get the value of a custom field or filter by a custom field value, you can write:

select

co.Name,

co.PipeColor

from

ComplianceObject co

where

co.PipeColor = 'Red'

 

PipeColor is the name of the custom field on the compliance object. If the custom field name consists of more than one word, use quotes around the name:

select

co.Name,

co."Pipe Color"

from

ComplianceObject co

where

co."Pipe Color" = 'Red'

 

If the object contains a custom field which has the same name as a native field, by default EQL will resolve it to the native field. For example, the custom field name is "UOM". On a numeric requirement, this is the same name as the native field "UOM". In this case there is no way to select the value of the custom field "UOM" for the requirement.

Each EQL query can have more than one Custom Field referenced from one or more referenced tables.

The following types of Custom Fields are supported:

  • ComplianceObjects bound Custom Fields (linked via CustomFieldTemplate and CalculationTemplate Form)
  • Datapoint bound Custom Fields (linked via Data Quality Template)

  • DataPointHistory bound Custom Fields (linked via Data Quality Template)

  • EventInstance bound Custom Fields (linked via EventTemplate Form)
  • WorkflowStep bound Custom Fields (linked via FormTemplate Form)
  • Activity bound Custom Fields (linked via MaterialActivityTemplate Form)
  • Material bound Custom Fields (linked via MaterialActivityTemplate Form).

All custom field types are supported. Some types require an extension of the syntax described below.

CalculationTemplate fields are requested with the prefix "Calculation":

select

c.Calculation."UdfName"

from ComplianceObject c

Hyperlink fields support the following syntax:

select

f."udfActivityProperty",

f."udfActivityProperty".value,

f."udfActivityProperty".label

from facility f

 

If an extension is not specified then value is retrieved. Thus f."udfActivityProperty" is the same as f."udfActivityProperty".value.

NumericLookup fields support the following syntax:

select

f."udfNumLookup",

f."udfNumLookup".label,

f."udfNumLookup".label.Invariant,

f."udfNumLookup".label.Localized,

f."udfNumLookup".value

from

facility f

 

Where value = numeric value, label = text label (1), Localized = text label (3), Invariant = text label (2)

For BooleanDropdown, use the same syntax as for NumericLookup.

TextDropdown, TextMultiSelection and Label can use the extensions “Localized” (3) and "Invariant" (2)

If an extension is not specified then value is retrieved. Thus f."udfNumLookup" is the same as f."udfNumLookup".value.

Historical custom fields support the following syntax:

select

f."udfHistorical".BeginDate,

f."udfHistorical".EndDate,

f."udfHistorical".Value

from

facility f

f."udfHistorical" is equal to f."udfHistorical".value.

Historical fields also support the extension .historical, so the same result can be obtained with:

select

f."udfHistorical".Historical

from

facility f

 

The result of both queries will contain three columns: begindate, enddate, value.

Note: The following UDF types support multiple values:

  • Historical. In this case, values are ordered by BeginDate
  • Multi-selection list box. In this case, the order of values is the same as shown in the Management System UI.
  • Linked dropdown list. In this case, the order of values is the same as in the Management System UI (from parent to child)
  • Citation Hyperlink. In this case, the order of values is the same as in the Management System UI.

If there are several custom fields with multiple values in the same select statement, then the result is represented as a Cartesian product.
