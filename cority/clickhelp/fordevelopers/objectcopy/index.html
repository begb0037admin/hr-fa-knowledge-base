Object Copy Tool

The Object Copy Tool automates the process of copying and pasting objects to create new system objects. The tool can be used only within a single System Model. It cannot be used to copy objects between System Models.

Object Copy Tool

Because the Object Copy Tool uses existing system model assets to create other objects, it is imperative that a thorough QA of the 'source' objects is performed. Use the Source Object Preparation Checklist below to be sure the objects that will be created will require as little editing as possible. It is recommended that testing be done in a copy of the Division, which can then be deleted as a whole after debugging.

Caution:   The Object Copy Tool obeys ALL the same rules as manual copy and paste operations. It is important to note that if there are any tasks with future due dates associated with the copied objects, the tasks will also be copied. Notifications scheduled to go out for upcoming due dates will be sent. Deletion of any objects with tasks will also cause the system to send "task deletion" emails to the assignee(s) and assignor. Email addresses are invalidated on the Sandbox database to prevent spam emails while testing in this environment. However, you must be aware of potential email notifications that may be sent when the bulk upload is replicated to Production.

Preparation

Consult any available build documents to identify all objects to be built in the system. These documents should be detailed enough to show the types of custom fields, the information that is to reside in all custom and standard fields, and any and all tasks.

  • Source Objects: Identify or create the objects you wish to replicate.

Identify and mark any assets located on the build document that are not currently in the system. Group the objects on the build document by like properties (as best as possible), and either (a) find a similar object to use as the source or (b) create a source object in the system from the build document.

Important:  Rigorous QA of the existing objects is STRONGLY recommended before the Object Copy Tool is used to copy them.

  • Target Locations: Identify the paths and the names that the copied objects will be replicated to. Create any initial System Model objects needed to copy objects to.
  • Custom Field Templates. Check that the correct Custom Field Templates are applied to the source objects. For similar objects with different Custom Field Templates you will need a source object for each object-template variation. (Property values may be edited after objects are created using the Object Properties Editing Tool, but this will entail more work.)
  • Document and Citation Associations. Check that all source objects have the correct document and citation associations. You can add/remove citation associations with the Citation Management Tool, but it will involve more work. If the resultant objects have different associations, it might be best to leave associations blank on the source object. All documents and citations must be created in the system first.
  • Source Object Properties and Custom Field Values. Check that all Standard and Custom Field information is filled in correctly. If the resultant objects have various field values, leave the source object's custom field blank.
  • Source Object-Task Associations. Check that any tasks associated with the source objects are pertinent to the new objects, or remove them. You can use a dummy user for assignor and an empty group for assignee, then edit the tasks later.
  • Task Due Dates. Check that all task due dates are far enough into the future (with respect to the notification schedule) that they can be adequately edited (where applicable), permissions granted and then reviewed/completed by the necessary parties. Only tasks with due dates in the future will be copied with objects; completed tasks in the past will not be copied. It might be best to create a toolbox area within the model and place the source objects there. In this case, you can edit the task information (e.g. modify due dates, notifications, start dates, enter place holder assignee and assignor information) without affecting the real tasks. Following the upload operation, you can edit the tasks appropriately.
  • Run a Task Report. Check that the task(s) on the selected source objects will not cause problems if copied a multitude of times. Where potential problems are identified, edit the tasks appropriately (copy the source object and paste into a toolbox area if necessary).

  • Calculation Limits and Notifications. For calculations, check that any source data will NOT exceed limits or, if this is a possibility, that all data notifications are removed. It might be best to create copies of the source parameters and use these as the source parameters in the upload file. There are two current situations that make this item important:

    Even if the parameters and calculations are copied together (so no data will be associated with the new calculation), if there are triggered tasks into the future, these tasks will be copied as well. For example, a calc has an exceedance in the last week and a task has been triggered which is due 30 days after the event. Since the triggered task is now in the future, it is copied with the new object, even though there is no data to support that event.

    If the parameter is outside the realm of the copied objects, the data on the new calculations will still exist and this data will be re-evaluated against limits.

  • Run a Data Report. Check that the source data used in calculations will not trigger any unwanted data notifications or will not exceed limits needlessly. This information will appear in the Message Center (Data Warnings, possibly Inbox). Emails could potentially go out if the calculations are set up to send data warnings using that method.

Once you have thoroughly QA'd the source objects to be used in the copy operation, you can prepare the upload file.

Caution:  Be sure that the Facility Time Zone is correct, both for parent source facilities and parent destination facilities, as this field cannot be edited later.

Run a System Properties Report to assist in identifying the source objects and preparing the upload file. Because you cannot output the path of any object other than a requirement, pick the Division Name, Facility/Program Name, Unit Name, and POI name so that the object path can be created using the Excel concatenation function. You can then copy and paste the object names and paths into your upload file, as shown:.

Template Fields

All fields on the Object Copy Tool Template are required.

Source Path: Location in the System Model of object to be copied (path from Locations & Programs root to parent object). Do not include the model name. Include a backslash ( "\") at the beginning but not at the end. See example below.

Source Name: Name of object to be copied.

Destination Path: Location of new object to be created (same path rules as above).

Destination Name: Name of new object to be created. Do not use special characters. Disallowed characters in names include: "\", "/", "[", "]". It is also recommended that you clean up and eliminate any extra white spaces and limit use of dashes to a simple dash (not the m-dash or n-dash). Note that dashes can often be changed by auto-correct features in other documents from which you may copy your object names, so be careful that this does not introduce characters such as m-dashes and n-dashes that may be hard to identify and thus edit later.

Include Children?: Copy children of source object (yes or no). This works the same as in a manual copy operation. If "Include Children?" is Yes, the source object and all of its child objects will be copied.

1 Source Path Source Name Destination Path Destination Name Include Children?
2 \Division\Facility\Unit\POI Requirement Name \Division\Facility\Unit\POI Requirement Name Yes

Note:   Since each line in the file is executed consecutively, order is important. Parent objects must be created before any child objects. Pay attention to other dependencies, such as calculation dependencies and requirements monitored by Event Logs, if they are not copied as a whole by including children.
