The Package Manifest

An EMS App package may optionally contain a single manifest file in its root, by the name of "manifest.xml".

The manifest file may be used to control how the server-side EMS App runtime manages the EMS App content.

The following EMS App settings are supported:

General Settings:

  • name
  • description
  • iconSrc – the path, relative to the EMS App package root directory, to an icon file.
  • displayPage – the path, relative to the EMS Apps package root directory, to an HTML page which will serve as the default page of the EMS App.
  • encoding – the text encoding to use for all Items content. By default, UTF-8 is used.
  • id – optional attribute, used chiefly for updating global apps across system.

1) Id must be a GUID (http://en.wikipedia.org/wiki/Globally_unique_identifier)

2) When specified:

a. Id will be used as ID of the App in the system in which it is uploaded. This allows for predicting the URL to the app as /CustomApp/<id>/…

b. When updating an existing app, the IDs must match, otherwise an error is thrown

Example: 

<package id=” f69ef02b-0951-4f95-893a-4b76115c4ac9” name=”MyApp”… >

..

</package>

Security Settings and Directives:

  • roles – one or more directives to create or remove Roles (see Role Directives)
  • permissions – permission settings for Items or App Data keys (see Permission Settings)
  • contentSecurityPolicy – browser CSP settings

Data Directives:

  • appData – one or more directives to save or remove App Data (see App Data Directives)
  • userData – one or more directives to remove User Data (see User Data Directives)

When uploading an EMS App package as part of an update of an existing EMS App, the manifest settings and directives in the package, if provided, will be used as follows:

  • Settings, such as General Settings, CSP Settings, and Permission Settings, will overwrite the existing settings for the EMS App.
  • Directives, such as Role and Data Directives, will be executed in the order in which they are declared in the manifest.

The following is an example of a manifest file, and illustrates the required order of element declaration as well. In your own manifest file, be sure to follow the same order of elements.

<?xml version="1.0"?>

<package displayPage="index.htm" iconSrc="icon.ico" encoding="UTF-8" name="My Package">

<description>Package demonstrating the EMS REST APIs.</description>

<contentSecurityPolicy

sandbox=""

defaultSrc="self"

connectSrc="https://api.enviance.com"

fontSrc="*.coolfonts.com"

frameSrc=""

scriptSrc="userscripts.example.com" />

<roles>

<add name="Manager" description="Managers for the plant."/>

<add name="Operator" description="Operators for the plant."/>

<remove name="Worker" />

</roles>

<appData>

<set key="Default Assignee" value="jsmith" />

<remove key="New Assignee" />

</appData>

<userData>

<remove key="My Default Query" />

</userData>

<permissions>

<appData key="Default Options">

<allowRead roles="Everyone" />

</appData>

<appData key="Admin Options">

<allowRead roles="Admins" />

<allowWrite roles="Admins" />

</appData>

<item path="/manage/manage_plant.htm">

<allow roles="Manager; Auditor" />

<deny roles="Operator" />

</item>

<item path="/operate.html">

<allow roles="Everyone" />

</item>

<item path="/test.html">

<deny roles="Everyone" />

</item>

</permissions>

</package>
